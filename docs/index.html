Pipeline explainer

Encode → Decode → Check 1 Entity → Check 2 Self-consistency → Check 3 Grad-CAM → Route. In the full report, a visual encoder (EfficientNet or BioViL-T) feeds a text decoder (ClinicalBERT or GPT-2). In this browser demo, that trained pipeline is replaced by an honest, transparent simulation: template drafts for three synthetic cases, plus the same three checks and the same routing rule. If any check fails, the report is never auto-emitted as a finished report — it goes to mandatory radiologist review.

Model Info (FR5)

  • Model version: v0.1-demo — transparent rule/template simulation, NOT a trained EfficientNet / BioViL-T / ClinicalBERT / GPT-2 model running in this browser.
  • Dataset: IU X-Ray — prototype simulation, not trained on it in this browser demo. IU X-Ray is cited from Indiana University / NIH Open-i; no dataset files are redistributed here.
  • Calibration / thresholds: Self-consistency threshold 0.60 across 5 decodings; entity check requires every named entity to be supported; Grad-CAM check requires attention inside the relevant anatomy.
  • Routing: Any failed check → MANDATORY RADIOLOGIST REVIEW; no finished report is auto-emitted.
  • Label: NOT FOR CLINICAL USE — AI-generated draft, requires radiologist review before any clinical use.
  • Cost: ₹0 for this demo (no paid services, no external CDN).

Safety & Limits

  • Coursework prototype only. This is not a clinical product, diagnosis, or validated medical device.
  • Do not use any draft on this page for patient care. A radiologist must review every draft before any clinical use.
  • Synthetic schematics only — no real patient images, and no images copied from the course presentation.
  • The demo does not measure BLEU, ROUGE, or CheXpert scores, and it does not claim the report's target thresholds were achieved.
  • Uploaded files are not analysed, not sent anywhere, and cannot produce a medical finding in this demo.
  • Known limits: three synthetic cases only; template drafts, not learned generation; Grad-CAM is a simulated region, not a computed gradient map from a trained encoder.

How this maps to the report

Functional requirements

  • FR1: Accept an image (demo cases, or a local upload routed to review) and return a draft impression, entity flag, and self-consistency score.
  • FR2: Entity-consistency check flags each unsupported entity by name — see Demo C, where pneumothorax is flagged NOT SUPPORTED.
  • FR3: A hallucination flag or self-consistency below threshold routes to mandatory review and is never returned as a final, unreviewed result.
  • FR4: Every generated output carries the provenance / not-for-clinical-use label, shown in the header, in every case output, and in the Python output.
  • FR5: Model Info panel above (version, dataset, calibration, not-for-clinical-use statement).
  • FR6: This static demo logs no images and no user data; a full service would log image statistics and metadata only, never raw images.

Non-functional requirements (report targets, NOT demo claims)

The report's targets — for example BLEU-4, ROUGE-L, ClinicalBERT-Score, CheXpert-F1, hallucination-rate ceiling, latency, and reproducibility — are design targets for a trained system. This demo does not claim to meet them, and no score is shown as achieved.

Life cycle — CRISP-DM (primary, with TDSP deployment discipline)

  • Business Understanding: clinical workload problem, non-clinical scope boundary, stakeholder map.
  • Data Understanding: IU X-Ray exploration, finding frequency, image quality, frontal vs lateral coverage.
  • Data Preparation: de-identification review, CheXpert labelling, patient-level splits.
  • Modelling: encoder/decoder fine-tuning in the full project; template simulation in this demo.
  • Evaluation: three-check hallucination detection, plus metric evaluation in the full project.
  • Deployment: GitHub Pages for this demo (docs/ folder); Docker / FastAPI service in the full project design, with CI gates and drift monitoring.
